**Кроссплатформенный дизассемблер, который работает прямо в браузере — офлайн, без установки и загрузки файлов на сервер.** Открывайте исполняемые файлы, динамические библиотеки, модули WebAssembly, сборки .NET, классы Java и архивы приложений. Исследуйте инструкции, функции, вызовы, строки, ссылки и метаданные бинарных файлов.

Весь инструмент помещается **в один автономный HTML-файл** — `build/disassembler.html`. Сохраните его на диск и откройте в современном браузере. Все файлы обрабатываются локально, а политика Content Security Policy (CSP) запрещает странице доступ к сети.

### Поддерживаемые платформы, форматы и архитектуры

| Платформа или среда | Форматы | Архитектуры или байт-код |
| --- | --- | --- |
| macOS | Mach-O, `.dylib`, универсальные бинарные файлы | arm64, arm64e, x86-64, i386 |
| iOS | Mach-O, `.ipa`, `.app` в ZIP | arm64, armv7 |
| Windows | PE `.exe`, `.dll` | x86-64, i386, arm64, ARM64EC, ARM64X, 32-битный Arm |
| Linux | Исполняемые файлы ELF, динамические библиотеки | x86-64, i386, arm64, 32-битный Arm |
| Android | ELF `.so`, `.apk`, `.aab`, `.apks`, `.xapk` | arm64-v8a, armeabi-v7a, x86_64, x86 |
| WebAssembly | Модули `.wasm` | Инструкции WebAssembly |
| .NET | Управляемые `.exe`, `.dll` | CIL (C#, F#, Visual Basic и другие языки CLI) |
| JVM | `.class`, `.jar`, `.war`, `.jmod`, `.aar` | Байт-код Java, включая код из Kotlin и Scala |

Инструкции отображаются в ассемблерной записи, с описаниями и статистикой. Для **arm64, x86-64, WebAssembly, .NET и Java** доступно также представление **[HLA64](https://github.com/marketkernel/html-hlaa64)** — более читаемая запись операций. HLA64 — ассемблер с высокоуровневыми синтаксическими конструкциями для ARM64, x64 и WebAssembly; в этом проекте его нотация расширена для CIL и байт-кода JVM.

## Начало работы

1. Выполните `./build.sh open` или `npm install && npm run build`, после чего откройте `build/disassembler.html`.
2. Нажмите **«Открыть программу»** или перетащите файл на страницу. Исполняемый файл macOS-приложения обычно находится по пути `Name.app/Contents/MacOS/Name` (в Finder — «Показать содержимое пакета»). Для универсального Mach-O по умолчанию выбирается срез arm64; другие архитектуры доступны на вкладке **Mach-O**.
3. Для Android можно открыть отдельную библиотеку `.so` или архив `.apk`, `.aab`, `.apks`, `.xapk`. Из архива выбирается нужная библиотека по ABI. Аналогично `.ipa` и упакованный `.app` позволяют выбрать исполняемый файл iOS-приложения, его фреймворк или расширение.
4. Windows `.exe` и `.dll`, сборки .NET, Java `.class` и `.jar` (также `.war`, `.jmod`, `.aar`), а также `.wasm` открываются напрямую. Модуль WebAssembly можно сохранить из вкладки **Network** инструментов разработчика браузера.
5. Дизассемблер декодирует инструкции и открывает листинг с функции `main`. Для ориентира: 2 миллиона инструкций обрабатываются примерно за секунду, 4 миллиона — приблизительно за полторы секунды.

| Раздел | Возможности |

## Представление HLA64

[HLA64](https://github.com/marketkernel/html-hlaa64) — не декомпилятор и не отдельный язык высокого уровня, а ассемблер с более читаемой записью стандартных операций. Например:

```text
x0 = [x1 + 8]
if x8 == 0 { goto L1000 }
push x29, x30
f()
```

В представлении HLA64 простые инструкции превращаются в присваивания, условия и вызовы. Связанные пары инструкций могут отображаться одной строкой: `cmp` вместе с условным переходом, `adrp` вместе с `add` или загрузкой адреса. Адрес, указывающий на строку или символ, показывается по имени, если его удалось определить.

Для операций, которых пока нет в исходном HLA64, добавлены новые обозначения: беззнаковые сравнения (`<u`, `>=u`), атомарные операции (`atomic_add`, `cas`), `udiv()`, `umulh()`, `load_acquire`, имена Rust и Objective-C, а также конструкции для стековых машин. Эти слова описаны в `src/data/hla64-words.json` и помечаются в листинге.

Для **x86-64** нотация используется с регистрами `rax`, `rcx` и другими, но только когда результат точно соответствует исходной инструкции. Например, реальный `push` не обязательно может быть показан как HLA64 `push`, потому что семантика этого оператора отличается. Для **i386** представления HLA64 нет.

Для **WebAssembly**, **CIL** и **JVM** инструмент сворачивает цепочки стековых операций в выражения, сохраняя порядок вычислений и побочные эффекты:

```text
l3 = sum(0x4b0, 8)
V_1 = Program::Sum(V_0, i32(len(V_0)))
p = new Point(3, 4)
System::out.println(concat("sum=", sum))
```

Если безопасно выразить операцию через более короткую конструкцию нельзя, она остаётся инструкцией или отображается как функция с явными операндами. Это важно для точности: HLA64 — другая форма представления того же кода, а не попытка восстановить исходную программу.

## Android: arm64-v8a и armeabi-v7a

Нативные библиотеки Android используют тот же интерфейс дизассемблирования; вкладку **Mach-O** заменяет **ELF**. Показываются ABI и минимальная версия Android, если их можно установить из заметки NDK или версий символов Bionic.

- **ELF** (`src/core/elf.ts`): 32- и 64-битные файлы, включая варианты без заголовков секций; таблицы символов, версии импортов, зависимости, REL/RELA/RELR, упакованные релокации Android APS2, GOT/PLT, build ID, BTI/PAC, атрибуты Arm, unwind-таблицы и массивы инициализации/завершения.
- **arm64-v8a**: дизассемблирование AArch64, анализ функций, строк и ссылок, представление HLA64.
- **armeabi-v7a** (`src/core/arm32/`): декодирование A32, T16 и T32. В одной секции могут смешиваться инструкции ARM, Thumb и данные. Если в библиотеке нет mapping symbols, анализ определяет режим инструкций по точкам входа, вызовам, таблицам развёртки стека, прологам, литеральным пулам и таблицам переходов. Данные в кодовой секции отображаются как `.word`.
- Поддерживаются целевые наборы инструкций Armv8.6-A AArch32, включая VFP/FP16, Advanced SIMD, криптографию, CRC, dot product, BF16 и матричные операции Int8.
- **Linux**-бинарные файлы arm64 и armhf проходят через тот же анализ. Даже в stripped-файле `main` может определяться по передаче адреса в `__libc_start_main`.

Результат AArch32-декодера проверяется сравнением с `llvm-objdump` на случайных кодировках и реальных библиотеках. Для 32-битного Arm представление HLA64 не предусмотрено.

## WebAssembly

Файл `.wasm` открывается в общем интерфейсе дизассемблера. Адреса инструкций соответствуют смещениям в файле, а адреса данных — линейной памяти модуля.

- **Декодер** (`src/core/wasm/`) поддерживает WebAssembly 3.0: MVP, sign extension, saturating conversions, bulk memory, reference types, multi-value, SIMD, relaxed SIMD, tail calls, exception handling, typed function references, GC, memory64, multiple memories, а также атомарные инструкции из предложения threads и wide arithmetic — всего **572 мнемоники**.
- **Модуль** (`src/core/wasm/module.ts`) содержит сведения обо всех секциях, функциях, типах, памяти, таблицах, глобальных переменных, сегментах данных и элементов, пользовательских секциях, `producers`, `target_features` и DWARF line tables.
- **Анализ** (`src/core/wasm/program.ts`) восстанавливает имена из секции `name`, импортов, экспортов и linking symbols, распознаёт имена Rust/C++, переходы по вложенным блокам, прямые и косвенные вызовы, строки и инструментарий, использованный для сборки (например, Emscripten, wasm-bindgen, Go или WASI).
- **HLA64** (`src/core/wasm/hla.ts`) преобразует цепочки стековых инструкций в выражения. `br_table` может отображаться как `switch`; при этом особенности семантики `block`, `loop` и `end` сохраняются.

`tools/verify-wasm.mjs` сравнивает декодирование с `wasm-tools print`: в описанных тестах совпали **9,8 млн** инструкций из реальных модулей и **2,1 млн** из случайно созданных модулей.

## .NET (CIL)

Сборка `.dll` или `.exe` с CLR-заголовком открывается как управляемая сборка. Поддерживаются C#, F#, Visual Basic и C++/CLI. IL-инструкции выводятся в формате `ildasm` с адресами внутри методов (`IL_001f`).

```text
IL_0007    ldstr      "--help"
IL_000c    call       bool [System.Runtime]System.String::op_Equality(string, string)
IL_0011    brfalse.s  IL_001f
```

- **Декодер** (`src/core/cil/`) поддерживает все **219** инструкций ECMA-335, включая префиксы, сигнатуры методов, generic-параметры, ссылки на сборки и специфические формы записи `ildasm`.
- **Метаданные** (`src/core/cil/metadata.ts`) включают CLI-заголовок, потоки `#~`, `#Strings`, `#US`, `#GUID`, `#Blob`, **45 таблиц** метаданных, тела методов и обработчики исключений.
- **Анализ** (`src/core/cil/program.ts`) группирует методы по типам, строит переходы, считает вызовы, собирает строки, определяет точки входа и ссылки на другие сборки.
- **Страницы «Сборка» и «Ссылки»** показывают имя, версию, target framework, runtime, strong name, ReadyToRun, ресурсы, импорты, P/Invoke и forwarded types.
- **HLA64** (`src/core/cil/hla.ts`) преобразует стековые вычисления в выражения, но не объединяет инструкции, если такое объединение может изменить смысл из-за типов, `NaN`, переполнения или меток переходов.

`tools/verify-cil.mjs` сравнивает результат с `ildasm` Microsoft: для **13,3 млн** инструкций .NET 10, F# и сборок JetBrains Rider различий не найдено в рамках проведённых тестов.

## Java (байт-код JVM)

Поддерживаются отдельные `.class` и архивы `.jar`, `.war`, `.jmod`, `.aar`. Архив анализируется как программа с набором классов, скомпилированных из Java, Kotlin, Scala или других языков JVM. Листинг воспроизводит формат `javap` и ссылки на constant pool.

```text
  8: ldc           #59    // String --help
 10: invokevirtual #61    // Method java/lang/String.equals:(Ljava/lang/Object;)Z
 13: ifeq          25
 67: invokestatic  #81    // Method sum:([II)J
```

- **Декодер** (`src/core/jvm/`) реализует **202** кода операций JVM с широкими формами (`iload_w`, `iinc_w` и др.), форматирует константы и ссылки так, как `javap -c -p`.
- **Чтение классов** (`src/core/jvm/classfile.ts`) обрабатывает constant pool, поля, методы, атрибуты, обработчики исключений, таблицы строк и локальных переменных, записи, sealed classes, модули, bootstrap methods и другие метаданные.
- **Анализ** (`src/core/jvm/program.ts`) строит дерево классов и методов, метки переходов, вызовы, импорты, строки и точку входа `Main-Class`.
- **«Классы» и «Ссылки»** показывают manifest, версии class-файлов, пакеты, зависимости и используемые внешние члены.
- **HLA64** (`src/core/jvm/hla.ts`) восстанавливает выражения со статическими и виртуальными вызовами, созданием объектов, массивами, лямбдами и конкатенацией строк.

Проверка `tools/verify-jvm.mjs` на JDK 25, IntelliJ IDEA и Android Studio охватывала **276 тыс. классов** и **52 млн инструкций** — без различий с `javap` в указанных тестах.

## Поддержка x86-64 и i386

Код x86-64 и i386 из ELF, PE и Mach-O выводится в синтаксисе Intel, совместимом с `llvm-objdump -M intel`.

- **Декодер** (`src/core/x86/`) использует таблицы, сгенерированные из описаний x86 в LLVM 21: базовые инструкции, x87, MMX, 3DNow!, SSE, AVX/AVX2, AVX-512, AVX10.2, AMX, APX, XOP, FMA4, криптографические и системные расширения. Сам декодер и форматирование инструкций написаны для проекта.
- **Анализ** (`src/core/x86/program.ts`) использует таблицы символов, экспорты, unwind-таблицы и вызовы для определения начала функций; восстанавливает обращения через GOT/PLT, ссылки на строки и таблицы `switch`.
- **Windows PE** (`src/core/pe.ts`) поддерживает PE32/PE32+, импорты и delay-load, экспорты и forwarders, `.pdata`, TLS callbacks, релокации, COFF-символы, PDB-ссылки, thunks и таблицы переходов. Управляемые .NET-сборки распознаются отдельно.
- **HLA64** доступен для x86-64, но не для i386.

В тестах `tools/verify-x86.mjs` результат сравнивается с `llvm-objdump` на **31 млн** случайных кодировок и многомиллионных исполняемых файлах и библиотеках, включая Flutter, WebRTC и программы macOS.

## Поддержка iOS и Objective-C

Программы iOS — это Mach-O. Архив `.ipa` содержит приложение в `Payload/Name.app`; дизассемблер показывает исполняемые файлы, фреймворки и расширения, читая `Info.plist` в двоичном или XML-формате. Для файла также отображаются данные бандла, версия и, при наличии, provisioning profile.

- **Objective-C** (`src/core/objc.ts`): метаданные runtime позволяют находить имена классов, категорий и методов даже в stripped-бинарниках, распознавать `objc_msgSend`-stubs, селекторы, ссылки на классы и литералы `NSString`.
- Поддерживаются старый формат dyld bind opcodes и chained fixups. Имена классов Swift, представленные в Objective-C runtime, показываются в читаемом виде.
- Приложения из App Store с зашифрованным FairPlay кодом (`cryptid 1`) распознаются, но не дизассемблируются. Дешифрованная копия (`cryptid 0`) открывается.

## Поддержка Windows on Arm

Нативные программы **arm64** обрабатываются декодером AArch64, а **32-битные Arm** (Windows RT/IoT, Thumb-2) — декодером AArch32. Поддерживается распознавание импортов через thunks, косвенные вызовы и таблицы исключений.

**ARM64EC** позволяет взаимодействовать коду Arm и x64 в одном процессе. **ARM64X** может содержать разные представления одного файла для процессов Arm и x64. Дизассемблер читает CHPE-метаданные и карты кода; вкладка **PE** позволяет переключаться между соответствующими представлениями. Смешанные файлы открываются с Arm-кодом, а x64-код доступен отдельно. Для stripped-программ разных архитектур анализ пытается определить `main` по последовательностям запуска C runtime.

## Изменение инструкций (macOS)

Выберите инструкцию и нажмите **«Изменить…»** (клавиша **E**). Новое значение можно ввести в виде ассемблерной команды (`mov w0, #1`, `b.ne 0x…`, `nop`), шестнадцатеричных байтов или выбрать одну из типичных замен: инвертировать условие, сделать безусловный переход, заменить команду на `nop`, вернуть 0 или 1.

Перед применением новая инструкция декодируется и показывается в предварительном просмотре. Изменение можно отменить, а кнопка **«Скачать»** сохраняет исправленный бинарный файл.

Для Mach-O на Apple Silicon изменение кода требует обновить подпись: проект пересчитывает SHA-256 хеши страниц и формирует **ad hoc** подпись, сохраняя entitlements. В универсальных файлах заново подписываются все срезы. Исходная подпись разработчика и notarization при этом теряются; для приложения в `.app` может понадобиться повторно подписать бандл:

```sh
codesign --force --deep -s - Name.app
```

`tests/patch.mjs` проверяет изменение, подпись, `codesign --verify --strict` и выполнение модифицированной программы на macOS.

## Как устроен дизассемблер

- **Декодер AArch64** (`src/core/arm64/`): собственная реализация таблиц A64 — арифметика, ветвления, системные инструкции, загрузки и сохранения, атомарные LSE-операции, операции с плавающей точкой, Advanced SIMD, FP16, BF16, Int8, FP8 и криптографические расширения. Форматирование учитывает псевдоинструкции и алиасы LLVM (`mov`, `cmp`, `lsl`, `cset`, `ubfx` и т. д.).
- **Чтение Mach-O** (`src/core/macho.ts`): универсальные файлы, сегменты и секции, символы, экспорты, fixups, подписи, информация о функциях и участках данных внутри кода. Поддерживаются также старые 32-битные бинарные файлы macOS/iOS.
- **Чтение ELF** (`src/core/elf.ts`) и **PE** (`src/core/pe.ts`): структуры бинарных файлов, символы, импорты, релокации, секции, зависимости и метаданные.
- **Восстановление имён**: C++ и Rust (`src/core/demangle.ts`), Swift (`src/core/swift.ts`), MSVC (`src/core/msvc.ts`). Swift- и MSVC-деманглеры сравниваются с `swift-demangle` и `llvm-undname`.
- **Анализ программы** (`src/core/program.ts`): инструкции, статистика, функции, метки, вызовы, ссылки на данные, строки и группы инструкций для HLA64.
- **Листинг** (`src/app/listing.ts`): миллионы строк представлены компактными типизированными массивами. Браузер создаёт элементы только для видимой части списка, а прокрутка сопоставляется с номерами инструкций.
- **Автономный HTML** (`build.mjs`): JavaScript и справочники сжимаются и встраиваются непосредственно в страницу. Объём встроенного кода после упаковки составляет примерно **1,2 МБ**; справочники разбираются по мере необходимости.
- **PWA** (`build/pages/`, `src/pwa/sw.js`): та же программа, но с манифестом и service worker для установки и автономной работы. Автономный `build/disassembler.html` при этом не зависит от дополнительных ресурсов.

`tools/verify-decoder.mjs` сопоставляет AArch64-декодер с `llvm-objdump`. В описанных проверках результат совпал на двухмиллионной Rust-программе; на движке Flutter для arm64-v8a была одна разница на 1,5 млн инструкций (LLVM распознал данные как SVE), а среди 4 млн случайных кодировок отличались лишь некоторые имена системных регистров и операций обслуживания TLB.

## Сборка и тестирование

Для сборки нужны **Node.js 22+**, TypeScript и esbuild. Для работы готового HTML-файла Node.js не требуется.

```sh
npm run check        # typecheck, unit tests, build, browser tests
npm test             # unit tests only (decoder vectors, AArch32, x86, WebAssembly, CIL, JVM, ELF and Android, patching, Mach-O, demangler, HLA64, data, i18n)
npm run build        # build/disassembler.html and build/pages/ (the PWA)
npm run watch        # rebuild on every change
npm run shots -- shots/ [program]     # screenshots of every screen
node tools/pwa-icons.mjs                         # the PWA's PNG icons, from assets/icon.svg (Chrome)
node tools/verify-decoder.mjs <program>          # against llvm-objdump (needs Xcode)
node tools/verify-decoder.mjs --random 1000000   # random encodings
node tools/verify-arm32.mjs <library.so>         # AArch32 against the NDK's llvm-objdump
node tools/verify-arm32.mjs --random 1000000 --set a32|t16|t32|thumb
node tools/verify-x86.mjs <program>              # x86 against llvm-objdump -M intel (Homebrew llvm@21)
node tools/verify-x86.mjs --random 1000000 [--mode 32] [--class evex]
node tools/x86-index.mjs <llvm-project>          # the x86 tables, from LLVM's X86 target
node tools/verify-swift.mjs <program …>           # Swift names against swift-demangle (Xcode)
node tools/verify-msvc.mjs <file …>              # MSVC names against llvm-undname (Homebrew llvm@21)
node tools/verify-wasm.mjs [module.wasm …]       # against wasm-tools print
node tools/verify-wasm.mjs --random 1000         # random modules from wasm-tools smith
node tools/verify-cil.mjs [assembly.dll …]       # CIL against Microsoft's ildasm
node tools/verify-jvm.mjs [file.jar|.class …]    # JVM bytecode against javap (JDK 23 or newer)
```

`npm run check` запускает проверку типов, модульные тесты, сборку и браузерные тесты. Для браузерных проверок используется установленный Chrome через протокол DevTools; путь можно задать переменной `CHROME`. Если Chrome не найден, эти проверки пропускаются.

Тесты включают небольшой пример `hello.c`, собранный для различных платформ, `.NET`- и Java-версии той же программы, наборы эталонных инструкций, iOS-приложение с Objective-C и Swift, Windows on Arm (включая ARM64EC/ARM64X) и ELF/Mach-O различных архитектур.

Для независимых сверок с существующими инструментами используются `llvm-objdump`, `wasm-tools`, `ildasm`, `javap`, `swift-demangle` и `llvm-undname`. Соответствующие скрипты расположены в `tools/verify-*.mjs`. Некоторые из них требуют Xcode, Android NDK, LLVM 21, JDK или .NET SDK — в зависимости от проверяемой платформы.

`tests/pwa.mjs` проверяет установку PWA, автономный запуск после отключения сервера и обновление при следующем развёртывании. Исходники и готовые результаты тестовых программ находятся в `tests/fixtures/`.

## Версии и релизы

Единственный источник версии — `package.json`. При сборке номер добавляется в страницу и имя кеша PWA. Если сборка выполнена из коммита с тегом `v<version>`, показывается версия релиза; иначе к ней добавляется хеш коммита, чтобы не путать текущую разработку со стабильной версией.

```sh
npm version minor        # 0.1.0 -> 0.2.0; обновляет package.json и тег v0.2.0
git push --follow-tags   # отправляет тег и запускает релизный workflow
```

Workflow `.github/workflows/release.yml` сверяет тег с `package.json`, запускает проверку типов и модульные тесты, затем прикладывает к релизу `disassembler-<tag>.html` и `SHA256SUMS.txt`. `.github/workflows/test.yml` запускает проверки на каждый push и pull request. Браузерные тесты обычно выполняются локально.

## Публикация через GitHub Pages

`.github/workflows/pages.yml` после каждого push в `main` собирает и тестирует проект, а затем публикует `build/pages/` на GitHub Pages. Адрес приложения: <https://disasm.marketkernel.com>.

При новом развёртывании обновляется версия кеша service worker. При наличии сети браузер загружает новую версию; уже открытое окно продолжает использовать прежний код до перезагрузки или нового запуска. Установленная PWA обновляется вместе с публикациями, а скачанный отдельный HTML-файл не меняется. Чтобы сохранить конкретную версию, скачайте её из релиза и проверьте по `SHA256SUMS.txt`.

## Переводы

Интерфейс поддерживает **английский и русский языки**: **«Настройки» → «Язык»** (системный, English или Русский). Переключение не требует повторного чтения открытого бинарного файла.

- Строки интерфейса задаются через `t(...)`, `tn(...)` или атрибут `data-i18n`; русский словарь находится в `src/locales/ru.json`.
- Локализованы также названия и описания инструкций, условий и слов HLA64. Английские JSON-файлы определяют структуру записи (формы, синтаксис, формулы и ссылки), а `.ru.json` содержат только переводимые тексты.
- `node tools/i18n.mjs` помогает найти отсутствующие и устаревшие переводы. `tests/i18n.mjs` проверяет полноту словаря, плейсхолдеры и формы множественного числа; `tests/data.mjs` — переводы справочников.
- Новый язык можно добавить через словарь в `src/locales/`, регистрацию в `src/core/i18n.ts` и файлы локализации в `src/data/`.

## Текущие ограничения

- Поддерживаются перечисленные выше архитектуры и форматы. **WebAssembly Component Model**, Dalvik-байт-код `classes.dex` из APK и ELF с обратным порядком байтов распознаются, но не разбираются. Инструкции FP16 и предложения stack switching для WebAssembly не декодируются; такие участки могут отображаться как `.bytes`.
- Инструкции **SVE** и **SME** показываются в виде `.inst`.
- Для смешанных C++/CLI и ReadyToRun-сборок .NET отображается **IL**, но не встроенный нативный код. Границы блоков `try` и обработчиков исключений отмечаются, однако структура блоков в точности как у `ildasm` не строится.
- В Java-архивах классы альтернативных версий из `META-INF/versions/…` учитываются, но не показываются. Вложенные JAR, например `BOOT-INF/lib` у Spring Boot, перечисляются, но не открываются автоматически.
- В stripped-библиотеках armeabi-v7a данные, на которые код нигде не ссылается, иногда могут выглядеть как инструкции — так же, как у `llvm-objdump` без mapping symbols.
- Начала функций определяются по символам, экспорту, `LC_FUNCTION_STARTS`, unwind-таблицам и целям вызовов. **Полного восстановления графа управления и декомпиляции нет**: инструмент показывает дизассемблированный код, метки и стрелки переходов.
- У старых i386-программ macOS не читаются метаданные legacy Objective-C runtime (`__OBJC`). Из Swift-метаданных извлекаются только имена классов, видимые Objective-C runtime; собственные дескрипторы типов и полей Swift не разбираются.
- Из DWARF читаются только таблицы соответствия исходным строкам. Строки Go без завершающего нулевого байта находятся только при наличии ссылок из кода.
