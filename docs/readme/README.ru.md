Откройте программу macOS — исполняемый файл приложения, `.dylib`, утилиту командной строки, для
Apple Silicon или Intel, 64-битную или старую i386, — приложение iOS (весь `.ipa`, arm64 или старое armv7), `.exe` или `.dll` Windows для x86-64, i386, arm64 (в том числе ARM64EC и ARM64X) или 32-битного Arm, нативную
библиотеку Android для arm64-v8a, armeabi-v7a, x86_64 или x86 (`.so` или весь `.apk`), программу
или библиотеку Linux для x86-64, i386, arm64 или 32-битного Arm, модуль
WebAssembly, сборку .NET — CIL из C#, F# или Visual Basic — или байт-код Java — `.class` или `.jar`
на Java, Kotlin или Scala, — и увидите каждую инструкцию: декодированную, объяснённую, посчитанную и — для arm64,
x86-64, WebAssembly, .NET и Java — записанную на ассемблере или на
[HLA64](https://github.com/marketkernel/html-hlaa64) — ассемблере с синтаксическим сахаром для
ARM64, x64 и WebAssembly.

Весь инструмент — одна самодостаточная страница `build/disassembler.html`. Она работает с
диска, без сети, в любом современном браузере. **Ничего никуда не отправляется**: файл читает
сама страница, а её Content-Security-Policy запрещает ей любой доступ к сети.

**Онлайн-версия: <https://disasm.marketkernel.com>** — та же страница как PWA (Progressive Web
App). Открытая один раз, она работает без сети: страница хранится в браузере и открывается без
подключения, а программы по-прежнему читаются с диска и никуда не загружаются. Её можно
установить в систему, и тогда она работает отдельным приложением, со своим окном и значком: на
компьютере, в Chrome, Edge и Arc, — кнопка установки в адресной строке; на iOS — «Поделиться» →
«На экран „Домой“».

**Или скачайте файл**: в каждом [релизе](https://github.com/MarketKernel/html-disasm/releases)
есть `disassembler-<версия>.html` — весь дизассемблер одним файлом, который можно держать на
диске и открывать в браузере совсем без сети, — и `SHA256SUMS.txt` для проверки.

## Как пользоваться

1. `./build.sh open` (или `npm install && npm run build`, затем откройте `build/disassembler.html`);
   нужны Node 22+ и Rust с целью WebAssembly (`rustup target add wasm32-unknown-unknown`).
2. Нажмите **Открыть программу** или перетащите файл на страницу. Программа приложения лежит
   внутри бандла: `Name.app/Contents/MacOS/Name` (в Finder — «Показать содержимое пакета»).
   Универсальные файлы открываются на срезе arm64; остальные срезы (x86_64, а у старых программ
   i386 или armv7) открываются со страницы **Mach-O**. Библиотека Android — это файл `.so`; `.apk`
   (или `.aab`, или набор split APK: `.apks`, `.xapk`) открывает список библиотек внутри по ABI,
   и выбранная извлекается и открывается. `.ipa` iOS (или `.app` в ZIP) так же показывает список:
   исполняемый файл приложения, его фреймворки и расширения. `.exe` или `.dll` Windows открываются как есть — и сборки .NET, чей IL записан так, как его пишет ildasm. `.class` или
   `.jar` Java (или `.war`, `.jmod`, `.aar`) открывается как одна программа — все её классы, байт-код записан так, как его пишет javap. Файл `.wasm` распознаётся по сигнатуре; модуль веб-страницы можно сохранить со
   вкладки «Сеть» инструментов разработчика браузера.
3. Страница декодирует все инструкции (2 миллиона — примерно за секунду, модуль из 4 миллионов —
   за полторы) и открывается на `main`.

## Каталог инструкций

`src/data/arm64-instructions.json` содержит все инструкции AArch64, кроме SVE и SME, —
1 194 мнемоники, — у каждой краткое название, описание простым языком, действие в виде
формулы, флаги, которые она читает или устанавливает, категория и формы с ассемблерным
синтаксисом и ссылкой на страницу документации Arm. Русские названия и описания — в
`src/data/arm64-instructions.ru.json`.

Перечень инструкций, их формы и синтаксис взяты из машиночитаемой спецификации Arm —
*A64 ISA XML for A-profile Architecture*. Собственный текст Arm защищён уведомлением,
запрещающим копирование, поэтому он не копируется: описания написаны для этого проекта, а
каждая форма ссылается на страницу Arm с первоисточником. `tests/data.mjs` проверяет, что
каждая запись полна и ни одно описание не похоже на текст спецификации.

`src/data/wasm-instructions.json` — то же для WebAssembly: 572 инструкции, у каждой название,
описание, действие и категория; коды операций, непосредственные операнды и стековые сигнатуры
берутся из таблицы декодера (`src/core/wasm/opcodes.ts`), а каждая форма ссылается на свой раздел
спецификации WebAssembly (или предложений threads, старых исключений и wide arithmetic). Русские
тексты — в `src/data/wasm-instructions.ru.json`.

`src/data/cil-instructions.json` содержит 219 инструкций CIL: название, описание и действие,
своими словами; коды операций, операнды и работа со стеком берутся из таблицы декодера
(`src/core/cil/opcodes.ts`), а каждая инструкция ссылается на свою страницу
`System.Reflection.Emit.OpCodes` на Microsoft Learn (у `no.` её нет — там ссылка на ECMA-335).
Русские тексты — в `src/data/cil-instructions.ru.json`.

`src/data/jvm-instructions.json` содержит 213 мнемоник, которые javap печатает для 202 кодов
операций JVM (у широких форм вроде `iload_w` — свои записи): название, описание и действие своими
словами; коды операций, операнды и работа со стеком берутся из таблицы декодера
(`src/core/jvm/opcodes.ts`), а каждая мнемоника ссылается на свою страницу в главе 6
спецификации виртуальной машины Java. Русские тексты — в `src/data/jvm-instructions.ru.json`.

Обновить формы из новой версии XML (описания сохраняются):

```sh
node tools/arm-index.mjs ~/Downloads/ISA_A64_xml_A_profile-2025-12
node tools/arm32-index.mjs ~/Downloads/ISA_AArch32_xml_A_profile-2025-12
```

`src/data/arm32-instructions.json` — то же для AArch32: A32 и T32, базовые инструкции,
плавающая точка, Advanced SIMD, криптография и поздние расширения (скалярные произведения,
BF16, матричное умножение Int8) — 485 мнемоник: все из *AArch32 ISA XML for A-profile
Architecture* от Arm и две, которые печатает LLVM, но у которых нет своей страницы (`trap`,
`hint`). Каждая форма указывает, в каких наборах инструкций она есть (A32, T32), и ссылается на
страницу Arm; описания свои, на английском и русском (`src/data/arm32-instructions.ru.json`).
Напечатанная мнемоника находит свою запись без условия и уточнений: `addeq` — это `add`,
`vaddeq.f32` — `vadd`, `bls` — `b`, `itte` — `it`.

## HLA64

HLA64 — ассемблер, а не новый язык: его программы — обычные инструкции плюс сахар для
очевидного — `x0 = [x1 + 8]`, `if x8 == 0 { goto L… }`, `push x29, x30`, `f()`. Режим HLA64
записывает каждую инструкцию этими словами, где подходящее есть, и оставляет инструкцию как
есть, где его нет, — HLA64 принимает её без изменений. Два соседа, имеющие смысл только
вместе, становятся одной строкой: сравнение и переход или выбор, проверяющий его флаги, и
`adrp` с `add` или загрузкой, достраивающей адрес, — тогда вместо адреса видна строка или
символ, на который он указывает.

Дизассемблированному коду нужны слова, которых в HLA64 пока нет: беззнаковые сравнения
(`<u`, `>=u`), `udiv()`, `umulh()`, атомарные операции (`atomic_add(u64[x0], x1, release)`,
`cas(…)`), `load_acquire`, имена, не являющиеся идентификаторами
(`` `core::fmt::Formatter::pad`() ``), строковые константы Objective-C (`x2 = @"Hello, %@!"`) и ещё несколько. Они лежат в
`src/data/hla64-words.json` вместе со словами самого языка, помечены `"new"` и подчёркнуты в
листинге; при наведении появляется объяснение. У каждого слова указано, какие режимы его пишут
(`targets`), и инструкции, которые оно заменяет на каждой платформе; режим WebAssembly добавляет
несколько своих — локальные переменные (`l3`), присваивание как значение (`(l3 = x)`), вызов через
таблицу (`table[i](a, b)`), преобразования (`i32(x)`, `f64u(x)`), инструкции как функции
(`i32x4.add(a, b)`).

Вид x86-64 (`crates/core/src/x86/hla.rs`) пишет те же слова над регистрами x86 — `rax = [rbp - 0x28]`,
`eax = u8[rdi + rcx]`, `rcx += rdx`, `if edi >u 7 { goto L… }`, `printf()`,
`atomic_add(u64[&counter], r14, seq_cst)` для `lock add` — и оставляет инструкцию везде, где сахар
означал бы другое: 8- или 16-битный регистр, сравнение с памятью, переход по флагу, который сахар не
может назвать (`cmovl` после `sub`), любая работа с `float` в xmm (значения xmm в HLA64 — double).
Собственные `push` и `pop` HLA64 на x64 хранят регистр в слоте кадра, поэтому настоящий `push rbx`
записывается тем, что он делает (`rsp -= 8; [rsp] = rbx`), а инструкция, которую HLA64 прочитал бы
как своё слово, — в `asm "…"`. Вида HLA64 для кода i386 нет: у HLA64 нет такой цели.

Режим для .NET (`crates/core/src/cil/hla.rs`) устроен как режим WebAssembly, только над локальными
переменными CIL (`V_0`), аргументами, полями, вызовами и массивами — `V_1 = Program::Sum(V_0,
i32(len(V_0)))`, `Console::WriteLine("usage")`, `V_0 += i64(values[V_1])`, — а его собственные слова
отмечены как новые; см. [.NET (CIL)](#net-cil). Так же устроен режим для Java
(`crates/core/src/jvm/hla.rs`) — над локальными переменными JVM (`i`, `l3`), полями, вызовами и
массивами: `sum = Hello::sum(values, len(values))`, `p = new Point(3, 4)`,
`System::out.println(concat("sum=", sum))`; см. [Java (байт-код JVM)](#java-байт-код-jvm).

## Android: arm64-v8a и armeabi-v7a

Библиотека Android открывается как программа, с теми же страницами; вкладка **Mach-O**
называется **ELF**. Плашка файла показывает ABI (`arm64-v8a`, `armeabi-v7a`) и самую старую
версию Android, на которой библиотека работает (`Android 7.0+`), — по заметке, которую оставляет
NDK; без заметки на Android указывают версии символов Bionic (`LIBC`), как версии glibc — на
Linux. Программа Mach-O так же показывает свою платформу (`macOS 14.0+`).

- **ELF** (`crates/core/src/elf.rs`, в ядре): 32- и 64-битные файлы, с заголовками секций и без них. Таблицы
  символов, нужные библиотеки и версии символов, по которым видно, из какой библиотеки импорт
  (`strcmp@LIBC`); релокации во всех видах, в каких их пишут линкеры, — REL, RELA, RELR и
  упакованные APS2 Android, — которые называют слоты GOT; заметка Android (уровень API, NDK),
  build ID, BTI/PAC, атрибуты сборки Arm; таблицы раскрутки (`.ARM.exidx`, `.eh_frame_hdr`) и
  массивы init/fini, по которым видны начала функций даже в библиотеке без таблицы символов.
  Заглушки PLT названы по слоту, через который прыгают, — импорт или `name@plt` для собственной
  экспортируемой функции библиотеки.
- **arm64-v8a** проходит тот же анализ arm64, что и программа Mach-O, вместе с режимом HLA64.
- **armeabi-v7a** (`src/core/arm32/`) — два набора инструкций в одной секции и константы среди
  инструкций. Библиотека с таблицей символов сама говорит символами разметки, какие байты A32,
  T32 или данные. Без неё — а таковы все библиотеки в APK — анализ выводит это сам
  (`crates/core/src/arm32/pass.rs`, `crates/core/src/native/arm32.rs`): символы, указатели init и PLT дают набор по своим адресам;
  вызовы дают его по своим целям (`blx` переключает, `bl` сохраняет), если байты там на него
  похожи; статические функции из таблицы раскрутки опознаются по прологу или по первым байтам,
  прочитанным обоими способами; слова, которые читают загрузки относительно PC (и `adr` с
  загрузкой после него), таблицы switch'ей (`tbb`/`tbh`, `add pc`/`ldr pc` в A32) и заполнение
  линкера между функциями — данные, показанные как `.word`. На libc++, рантайме ASan и libomp из
  NDK без таблицы символов результат расходится с их символами разметки на 10, 43 и 4 инструкциях
  из 180 000, 176 000 и 157 000; в движке Flutter не декодируются 116 слов из 1,86 миллиона.
  `ldr rX, [pc, #…]` и следующий за ним `add rX, pc`, `movw`/`movt`, `adr` и загрузки из слотов
  GOT называют строки, глобальные переменные и импорт, адрес которых строят; IT-блоки делают
  условными инструкции после себя; у switch'ей варианты становятся целями переходов.
- **Программы Linux** для arm64 и armhf (glibc) проходят тот же анализ. В программе без таблицы
  символов `main` — то, что `_start` передаёт в `__libc_start_main`: адрес из `adr`, из `adrp` +
  `add`, из литерала или из слота GOT.
- **Декодер** (`a32.ts`, `thumb.ts`, `simd*.ts`): A32, T16 и T32 из AArch32 Armv8.6-A —
  целочисленные, системные и сопроцессорные инструкции, VFP с FP16, Advanced SIMD,
  криптография, CRC, скалярные произведения, BF16, матричное умножение Int8. Он печатает то же,
  что llvm-objdump, IT-блоки считает так же, как LLVM, а `tools/verify-arm32.mjs` сверяет их
  построчно: на 5 миллионах случайных слов A32, 4 миллионах случайных T32 и потоков Thumb и на
  четырёх настоящих библиотеках выше (660 000 инструкций) расхождений нет.
- Режима HLA64 для 32-битного кода Arm нет: у HLA64 нет такой цели.

## WebAssembly

Файл `.wasm` открывается как программа, с теми же страницами. Адреса кода — смещения в файле, как
их показывают инструменты разработчика браузеров; адреса данных — адреса в линейной памяти модуля.

- **Декодер** (`crates/core/src/wasm/decode.rs`, в ядре): все инструкции WebAssembly 3.0 — MVP, знаковое расширение,
  преобразования с насыщением, групповые операции с памятью, ссылочные типы, multi-value, SIMD и
  relaxed SIMD, хвостовые вызовы, обработка исключений (и старые `try`/`catch`), типизированные
  ссылки на функции, GC, memory64 и несколько памятей, — а также атомарные операции предложения
  threads и wide arithmetic: 572 мнемоники. Он печатает текстовый формат ровно так, как
  `wasm-tools print`, а `tools/verify-wasm.mjs` сверяет их построчно: 39 миллионов инструкций 40
  настоящих модулей (Go, Rust, C++ с relaxed SIMD, side-модули Emscripten, esbuild, tesseract) и
  инструкции случайных модулей со всеми включёнными предложениями — без единого расхождения.
  Инструкции строк на экране страница спрашивает у ядра.
- **Модуль** (`crates/core/src/wasm/module.rs`, в ядре, передаётся странице в JSON;
  `tools/diff-wasm-module.mjs` сверяет то, что видит страница, с прежним чтением на TypeScript, в
  том числе на повреждённых модулях): все секции, включая rec-группы GC-типов, сегменты
  элементов и данных всех видов, теги и пользовательские секции, которые оставляют инструменты:
  `name` (функции, локальные, глобальные, данные, типы…), `producers`, `target_features`,
  `dylink.0`, `linking` и `reloc.*` объектных файлов, `sourceMappingURL`, `build_id`; а также
  таблицы строк DWARF (`crates/core/src/wasm/dwarf.rs`), которые ставят рядом с кодом файл и строку
  исходника.
- **Анализ** (`crates/core/src/wasm/program.rs`, в ядре): имена функций из секции имён, символов linking,
  экспорта и импорта (имена Rust и C++ деманглируются); метки по вложенности блоков, так что у
  `br 1` есть адрес и стрелка; вызовы, а для `call_indirect` — функции его типа в таблицах; строки
  в сегментах данных и константы, которые на них указывают, — в том числе в пассивных сегментах,
  которые стартовая функция многопоточного модуля копирует через `memory.init`; набор
  инструментов (Emscripten, wasm-bindgen, Go, WASI…). 4,2 миллиона инструкций esbuild
  анализируются примерно за 0,3 с — в три-пять раз быстрее, чем прежним TypeScript.
- **HLA64** (`crates/core/src/wasm/hla.rs`): у HLA64 есть цель WebAssembly, поэтому режим тот же.
  Инструкции стековой машины сворачиваются обратно в операторы, которые они вычисляют, —
  `l3 = sum(0x4b0, 8)` вместо четырёх инструкций, — стек вычисляется выражениями; строка значит
  ровно то же, что её инструкции, операнды — в порядке вычисления. `select` становится
  `c ? a : b`, только когда ни у одной его части нет действия, `br_table` — `switch` со
  сгруппированными вариантами, `if` с условием — `if c {`. `block`, `loop` и `end` остаются
  инструкциями, потому что собственный `loop { }` HLA64 повторяется, а цикл WebAssembly — нет;
  переходы — это `goto` на метки. Инструкции без своего сахара записываются как функции от
  операндов (`i32x4.add(a, b)`). На всех проверенных настоящих модулях каждый оператор читается
  одной строкой.

## .NET (CIL)

Сборка .NET — `.dll` или `.exe` с заголовком CLR, из C#, F#, Visual Basic или C++/CLI, —
открывается как любая программа Windows, а кодом считается её IL. Адрес инструкции — её RVA;
листинг пишет его, как ildasm, смещением внутри метода (`IL_001f`).

```
IL_0007    ldstr      "--help"
IL_000c    call       bool [System.Runtime]System.String::op_Equality(string, string)
IL_0011    brfalse.s  IL_001f
IL_00a8    ldsfld     class [System.Runtime]System.Func`2<int32,int32> Hello.Program/'<>c'::'<>9__6_0'
IL_014a    call       !!0 Hello.Program::Largest<string>(class [System.Collections]System.Collections.Generic.List`1<!!0>)
```

- **Декодер** (`crates/core/src/cil/decode.rs` и `page.rs`, в ядре): все 219 кодов операций раздела III ECMA-335, включая префиксы,
  напечатанные так, как их печатает ildasm от Microsoft, вместе с операндами: методы и поля с
  сигнатурами и сборками, обобщённые экземпляры, указатели на функции, имена в кавычках
  (`'<>c'`, `'value'`), строки не из чистого ASCII в виде `bytearray (…)`, числа с плавающей
  точкой так, как их пишет `%g` из C, а NaN и бесконечности — их байтами. Там, где у ildasm свои
  причуды, — какие обобщённые параметры он называет по имени (`!T`), а какие по номеру (`!0`),
  где переносит список параметров на новую строку (здесь это `, ` против голой `,`), — правила
  взяты из его исходников. `tools/verify-cil.mjs` сверяет текст, который показывает страница, с ildasm построчно: все методы
  172 сборок общего фреймворка .NET 10 (2,7 миллиона инструкций, в том числе
  System.Private.CoreLib), компилятора и базовой библиотеки F# (1,9 миллиона) и 155 сборок
  JetBrains Rider (8,6 миллиона) — 13,3 миллиона инструкций без единого расхождения. Инструкции
  строк на экране страница спрашивает у ядра.
- **Метаданные** (`crates/core/src/cil/metadata.rs`, `names.rs`, в ядре): заголовок CLI, корень
  метаданных и его потоки (`#~` или `#-`, `#Strings`, `#US`, `#GUID`, `#Blob`), все 45 таблиц,
  тела методов с короткими или полными заголовками и обработчиками исключений, сигнатуры типов,
  методов, полей и локальных переменных. То, что страница показывает из них, — карточка метода и
  его заголовок HLA64, страницы «Сборка» и «Ссылки» — тоже пишется там (`page.rs`), когда
  показывается, а `tools/diff-cil-page.mjs` сверяет это с прежним чтением метаданных на TypeScript.
- **Анализ** (`crates/core/src/cil/program.rs`, в ядре, которое само читает метаданные и пишет
  имена): каждый метод с телом — функция с именем
  `Namespace.Type::Method`, функции сгруппированы по типам; переходы, `switch` и обработчики
  исключений дают метки, а начала блоков try и обработчиков отмечены; вызовы считаются для
  методов этой сборки — и через MemberRef, если его класс — обобщённый класс, определённый здесь,
  — и для членов других сборок, которые и есть импорт; строки — это строки `#US`; целевая
  платформа берётся из `TargetFrameworkAttribute`, точка входа — из заголовка CLI.
  FSharp.Compiler.Service (1,6 миллиона инструкций) анализируется примерно за 0,4 с — вдвое
  быстрее, чем прежним TypeScript.
- Страница **Сборка** показывает манифест (имя, версию, культуру, открытый ключ, MVID), целевую
  платформу и среду выполнения, флаги CLI, строгое имя и ReadyToRun, потоки и таблицы
  метаданных, ресурсы и типы; **Ссылки** — сборки, с которыми она собрана, члены этих сборок,
  которые использует её код, P/Invoke и перенаправленные типы.
- **HLA64** (`crates/core/src/cil/hla.rs`): тот же режим, что у WebAssembly, — инструкции стековой
  машины свёрнуты обратно в операторы, которые они вычисляют: `V_1 = Program::Sum(V_0,
  i32(len(V_0)))` вместо шести, `if len(args) == 0 { goto IL_001f }`, `V_0 += i64(values[V_1])`,
  `(&V_0).n = n`, `new List<string>()`. Локальные переменные — `V_n`, аргументы — по именам; поля и
  методы — `obj.f` и `Type::f`, `Type::M(…)` для обычного вызова и `obj.M(…)` для виртуального
  (callvirt), типы — короткими именами с обобщёнными аргументами. Слово пишется только там, где
  оно означает ровно эти инструкции: каждое значение знает, целое ли оно, с плавающей точкой,
  ссылка или указатель — из сигнатур локальных переменных, аргументов, полей и методов, — поэтому
  `>u` пишется только между целыми, переход по false обращается только там, где NaN не может
  изменить смысл, `%` — только между целыми; `dup` сворачивается, только если копирует переменную
  или константу, и ни одно значение не переходит через метку или начало обработчика. То, для
  чего слова нет, остаётся инструкцией (`leave`, `endfinally`, префиксы) или записывается
  функцией от операндов (`add.ovf(a, b)`, `box<Kind>(x)`). В общем фреймворке .NET 10 и
  библиотеках F# на HLA64 читаются 68% строк — 87% инструкций.

## Java (байт-код JVM)

Файл `.class`, `.jar` (или `.war`, `.jmod` из JDK, `.aar` библиотеки Android — из него читается
`classes.jar`) открывается как одна программа: все классы внутри, написанные на Java, Kotlin, Scala
или чём угодно ещё, что компилируется для JVM. У файла класса нет адресов, поэтому коду каждого
метода отводится своё место; листинг пишет инструкцию на её pc, как javap, а после `//` — то, что
называет индекс пула констант.

```
  8: ldc           #59    // String --help
 10: invokevirtual #61    // Method java/lang/String.equals:(Ljava/lang/Object;)Z
 13: ifeq          25
 67: invokestatic  #81    // Method sum:([II)J
107: invokedynamic #103,  0  // InvokeDynamic #0:makeConcatWithConstants:(JLjava/lang/String;Ljava/lang/String;)Ljava/lang/String;
```

- **Декодер** (`crates/core/src/jvm/decode.rs`, в ядре): все 202 кода операций спецификации JVM, а широкие формы названы
  так, как их называет javap из JDK 25 (`iload_w`, `iinc_w`), напечатанные так, как их печатает
  `javap -c -p`: константы с комментариями javap (`// Method …`, `// InterfaceMethod …`,
  `// class "[I"`), член самого класса — без класса, имена, не являющиеся двоичными именами Java,
  — в кавычках (`"<init>"`), строки с экранированием Java, числа с плавающей точкой так, как их
  пишут `Double.toString` и `Float.toString` в Java (кратчайшие цифры, `4.9E-324`, при равенстве —
  к чётной цифре), switch с вариантами, а `jsr` и `ret` — без операндов, которые javap опускает.
  `tools/verify-jvm.mjs` сверяет текст, который показывает страница, с javap построчно: все методы
  69 модулей JDK 25 и JAR из IntelliJ IDEA и Android Studio — 276 000 классов, 52 миллиона
  инструкций — без единого расхождения. Инструкции строк на экране страница спрашивает у ядра.
- **Файлы классов** (`crates/core/src/jvm/classfile.rs`, в ядре): пул констант (с его модифицированным UTF-8),
  класс, его поля и методы и атрибуты, которые показывают страницы: Code с таблицей исключений,
  номерами строк и локальными переменными, загрузочные методы invokedynamic, исходный файл,
  сигнатуры, вложенные классы, записи, запечатанные классы, гнёзда и модули. То, что страница
  показывает из них, — инструкция с комментарием javap и локальной переменной, которую она читает,
  карточка метода и его заголовок HLA64, карточка класса, модуль — тоже пишется там (`page.rs`),
  когда показывается, а `tools/diff-jvm-page.mjs` сверяет это с прежним чтением классов на TypeScript.
- **Анализ** (`crates/core/src/jvm/program.rs`, в ядре): каждый метод с кодом — функция с именем
  `package.Class::method`, функции сгруппированы по классам; переходы, switch и обработчики
  исключений дают метки (`L25`), а начала защищённых диапазонов и обработчиков отмечены; вызовы
  считаются для методов программы — их ищут в названном классе, его предках и интерфейсах — и для
  членов классов, которых в ней нет, — это её импорт; тела лямбд и ссылок на методы считаются
  взятыми; строки — те, что загружает `ldc`; точка входа — `Main-Class` из JAR. java.base из JDK
  (7 300 классов, 1,7 миллиона инструкций) читается и анализируется примерно за 0,6 с — вдвое
  быстрее, чем прежним TypeScript, и в половине памяти: классы остаются в ядре, и оно снова читает
  класс, только когда страница показывает что-то из него.
- Страница **Классы** показывает манифест JAR, версии файлов классов (от Java 5 до Java 25), Kotlin,
  если у классов есть `kotlin.Metadata`, модуль, классы и другие файлы; для одного класса — его
  предка, интерфейсы и атрибуты. **Ссылки** — пакеты и классы других библиотек, которыми
  пользуется код, и их члены, которые он вызывает и читает.
- **HLA64** (`crates/core/src/jvm/hla.rs`): стек свёрнут обратно в операторы, как у .NET, —
  `sum = Hello::sum(values, len(values))`, `total += i64(values[i])`,
  `values = new int[8] { 1, 2, 3, 4, 5, 6, 7, 8 }`, `p = new Point(3, 4)` вместо `new`, `dup` и
  конструктора, `concat("sum=", sum)` для конкатенации строк и
  `` lambda<IntUnaryOperator, Hello::`lambda$main$0`>() `` для лямбды. Локальные переменные — по
  именам, которые хранит класс (`LocalVariableTable`, `MethodParameters`), если имя означает один
  слот, иначе `l3`; поля и методы — `obj.f` и `Class::f`, `Class::m(…)` для статического или
  точного вызова и `obj.m(…)` для виртуального. Инструкции JVM сами говорят, над чем работают,
  поэтому сравнение чисел с плавающей точкой соединяется с переходом только там, где NaN не меняет
  смысла: `fcmpl; ifge` — это `if a >= b`, а `dcmpg; ifge` остаётся `if dcmpg(a, b) >= 0`. В
  java.base на HLA64 читаются 77% строк — 94% инструкций; в собственном коде IntelliJ, во многом
  на Kotlin, — 55% и 79%.

## x86-64 и i386

Программа или библиотека Linux, библиотека Android для x86_64 или x86 и срез x86_64 программы
macOS открываются так же, как остальные, с теми же страницами; листинг — в синтаксисе Intel, как
его печатает llvm-objdump с `-M intel`.

- **Декодер** (`src/core/x86/`): все инструкции, которые знает LLVM 21, в 64- и 32-битном
  режимах — основной набор с APX (REX2, новый приёмник данных, `{nf}`, `ccmp`), x87, MMX и
  3DNow!, SSE до SSE4.2, AVX и AVX2, AVX-512 с масками, трансляцией и округлением, AVX10.2,
  AMX, XOP, FMA4, криптографические и системные расширения, — читаются так же, как их читает
  дизассемблер X86 в LLVM: префиксы дают контекст, контекст и код операции — инструкцию,
  инструкция — где лежит каждый операнд. Какую инструкцию выбирает каждая кодировка, где
  закодированы её операнды и как она пишется в синтаксисе Intel — это таблицы, которые
  `tools/x86-index.mjs` генерирует из описания цели X86 в LLVM и которые хранятся сжатыми
  (180 КБ); декодер и печать, которые их читают, написаны для этого проекта.
  `tools/verify-x86.mjs` построчно сверяет их с llvm-objdump: на 31 миллионе случайных
  кодировок по всем картам кодов операций и префиксам в обоих режимах, на движке Flutter
  (1,9 миллиона инструкций), WebRTC (3 миллиона), шести программах macOS (15 миллионов, C++,
  Objective-C и Rust) и рантаймах NDK для i686 и x86_64 не отличается ни одна строка — вплоть до
  того, что LLVM делает с байтами, которые не декодируются (пропускает прочитанные байты, и
  листинг тоже).
- **Анализ** (`crates/core/src/x86/pass.rs`, `crates/core/src/native/x86.rs`, в ядре): код режется на инструкции так же, как это делает
  llvm-objdump, — проходом по каждой секции кода, который начинается заново там, где символ,
  экспорт, таблица раскрутки или вызов говорят, что начинается функция. Данные именуются по
  операндам относительно rip на x86-64, по абсолютным адресам в коде, который не является
  позиционно-независимым, а в PIC-коде i386 — по регистру GOT, который код получает через `call` /
  `pop` (или `__x86.get_pc_thunk`) и `add`; вызовы и переходы через слот GOT, PLT или заглушку
  Mach-O называют импорт. Переключатели (switch) через таблицу — смещений от таблицы (PIC
  x86-64), от GOT (PIC i386) или адресов — получают свои ветви по проверке границ перед ними;
  таблица внутри секции кода показывается как данные `.long`. `main` программы без символов
  находится по тому, что `_start` передаёт в `__libc_start_main`.
- **Каталог** (`src/data/x86-instructions.json`): 1 805 мнемоник, у каждой — описание на
  английском и русском, написанное для этого проекта, формы — кодировка так, как её пишут
  руководства (`REX.W 01 /r`, `EVEX.512.66.0F.W0 FE /r`), синтаксис с видами операндов и нужные
  расширения — из LLVM и ссылка на её страницу в HTML-издании руководства Intel. `jne` находит
  `jcc`, `cmovge` — `cmovcc`, `cmpltps` — `cmpps`.
- **Windows** (`crates/core/src/pe.rs`, в ядре): исполняемые файлы и DLL формата PE32 и PE32+ — таблица импорта
  и таблица отложенного импорта со слотом каждого импорта в таблице адресов импорта, так что
  `call qword ptr [rip + …]` называет свою функцию; экспорт, включая перенаправления; таблица
  исключений (`.pdata`), в которой перечислены начала всех функций с данными раскрутки — даже в
  программе без символов; обратные вызовы TLS, релокации, символы COFF, если компоновщик их
  оставил, запись CodeView с именем PDB. Читается и то, что оставляют MSVC и MinGW: заглушки
  импорта (`jmp qword ptr [__imp_puts]`) — это импорт; таблица заглушек `jmp`, через которую
  вызывает код при инкрементальной компоновке, — по функции на каждую заглушку, названной по её
  цели (`j_имя`); переключатели через таблицу RVA от `__ImageBase` получают свои ветви;
  заполнение `int3` между функциями — одна строка (`int3 × 1 234`). Сборка .NET распознаётся и
  отклоняется (её код — CIL); Windows на Arm описана [ниже](#windows-на-arm). Официальные
  сборки SQLite для Windows (MSVC: оболочка x64 — 1,5 миллиона инструкций — и DLL для x86 и x64)
  декодируются в точности как в llvm-objdump.
- Вид HLA64 для x86-64 описан в разделе [HLA64](#hla64); у кода i386 его нет.

## iOS и Objective-C

Программа iOS — такой же файл Mach-O для arm64, как программа для Mac, и открывается так же;
`.ipa` — это ZIP-файл с приложением в `Payload/Name.app`, и при открытии он показывает, что в нём
можно запустить, — исполняемый файл приложения, его фреймворки и расширения, каждый по своему
`Info.plist` (`CFBundleExecutable`; двоичные и XML-списки свойств читает `crates/core/src/plist.rs`), —
чтобы выбранный извлечь и открыть (`crates/core/src/bundle.rs`, в ядре, которое его и распаковывает;
приложение macOS в ZIP открывается так же; `tools/diff-archive.mjs` сверяет чтение с прежним TypeScript).
Страница **Mach-O** тогда показывает бандл, его версию, нужную систему и — из
`embedded.mobileprovision` — кто его подписал, для каких устройств и до какого срока.

- **Objective-C** (`crates/core/src/objc.rs`, в ядре; странице приходит вместе с образом): собственные метаданные среды выполнения, которые остаются
  и в программе без таблицы символов, — список классов и список категорий, данные каждого класса
  только для чтения и его метакласс, списки методов в обоих видах (три указателя на метод или,
  начиная с Xcode 12, три 32-битных смещения). Каждый метод получает имя как функция
  (`-[Greeter initWithName:]`, `+[Greeter defaultGreeter]`), а каждая заглушка в `__objc_stubs` —
  имя по селектору, который она посылает, как её назвал компоновщик
  (`objc_msgSend$initWithName:`). Названо и то, что загружает код: ссылка на селектор
  (`selref.init`), ссылка на класс (`classref.NSString`), константа NSString (`@"Hello, %@!"`).
  Классы Swift записываются по-свифтовски (`_TtC8HelloKit7Counter` — это `HelloKit.Counter`).
  Указатели читаются через оба вида исправлений dyld: цепочки (chained fixups — каждый rebase и
  bind цепочки, до последнего звена) и старые коды привязки (bind opcodes). На фреймворках
  приложения iOS (Sentry, Firebase, Protobuf, WebRTC…) и на приложениях macOS (CotEditor,
  Kindle, Calculator), для arm64, arm64e и x86_64, методы и их адреса те же, что выводит
  `xcrun dyld_info -objc`; там, где он пишет `(null)` для класса Swift с именем `@objc`,
  страница называет его.
- **Шифрование**: у приложения из App Store код зашифрован FairPlay (`LC_ENCRYPTION_INFO_64`,
  `cryptid 1`), пока его не расшифрует устройство, на котором оно запускается. Такой файл
  распознаётся и отклоняется; копия, расшифрованная на устройстве (`cryptid 0`), открывается.

## Windows на Arm

- Программы **arm64** идут через анализ arm64, программы для **32-битного Arm** (Windows RT, IoT:
  только Thumb-2) — через анализ AArch32. Импорт называется и тогда, когда код вызывает его через
  заглушку (MinGW: `adrp x16; ldr x16, [x16, #…]; br x16`, `movw r12; movt r12; ldr.w pc, [r12]`),
  и тогда, когда — как у MSVC — слот импорта загружается в регистр и вызов идёт через него
  (`ldr x8, [x8, #…]; blr x8`, в том числе из регистра, сохраняемого между вызовами); на
  32-битном Arm пары `movw`/`movt` и слова литерального пула здесь — абсолютные адреса, а не
  смещения от pc. Начала функций берутся из таблицы исключений.
- **ARM64EC и ARM64X**: код Arm по соглашениям x64, чтобы код x64 в том же процессе мог вызывать
  его и вызываться им; файл ARM64X добавляет обычный код arm64 для процессов Arm, а процесс x64
  видит другой его вид, который делают динамические релокации из конфигурации загрузки (они
  переписывают заголовок: машину, экспорт, импорт). Метаданные CHPE говорят, какой код какой
  (карта кода), где начинаются функции ARM64EC и какая точка входа x64 стоит за какой из них. Такой
  файл открывается на коде Arm, а код x64 остаётся данными; страница **PE** показывает карту кода и
  открывает код x64, названный по экспорту вида x64. DLL ARM64X от Microsoft (dbghelp, symsrv,
  msdia140: 1,6 миллиона инструкций Arm и их код x64) декодируются так же, как в llvm-objdump,
  который переключает декодеры по той же карте кода.
- **main**: в программе Windows без таблицы символов его выдаёт запуск среды выполнения C — вызов
  после того, как среда отдала окружение или командную строку (MSVC со средой в DLL), вызов, который
  получает argc из результата `__p___argc`, базу образа (`WinMain`) или argc, argv и envp из
  глобальных переменных (MSVC со встроенной средой, новой и старой), вызов прямо перед `_cexit`
  (MinGW). Страница открывается там; для программ x86-64 и i386 это работает так же.

## Изменение инструкций (macOS)

Нажмите на инструкцию и **Изменить…** (клавиша **E**): откроется окно, где новую инструкцию
можно ввести ассемблером (`mov w0, #1`, `b.ne 0x…`, `nop`), байтами в hex или выбрать из
подходящих замен — обратное условие, безусловный переход, «ничего не делать», «вернуть 0/1».
Введённое декодируется и показывается до применения, поэтому в файл попадает ровно то, что
видно в предпросмотре, и никогда не слово, которое декодируется во что-то другое: ассемблер
(`crates/core/src/arm64/encode.rs`) проверяет каждую инструкцию, декодируя её обратно;
`tools/diff-assembler.mjs` сверяет его с ассемблером на TypeScript, который он заменил, слово в
слово и ошибка в ошибку, примерно на 16 миллионах строк.

Изменение сразу записывается в открытый файл; в листинге строки помечаются, изменение можно
отменить. **Скачать** сохраняет изменённый файл. Подпись кода программы macOS содержит хэш
каждой страницы, и Apple Silicon не запустит код arm64, у которого страницы не совпадают,
поэтому файл переподписывается ad hoc — так же, как `codesign --sign -` и линкер
(`crates/core/src/sign.rs`, в ядре): хэши страниц считаются заново (SHA-256 или те SHA-1 и SHA-384,
которые называет директория кода, — собственным `sha.rs` ядра; `tools/diff-resign.mjs` сверяет
подписанные файлы с теми, что подписывал прежний TypeScript крипто-библиотекой браузера), ставится флаг ad hoc, идентификатор команды и подпись Developer ID
убираются, права (entitlements) остаются. В универсальном файле переподписывается каждый срез —
и изменённый, и остальные. Файл, подписанный разработчиком, теряет эту подпись и нотаризацию,
поэтому при первом запуске macOS может попросить подтверждение; если он внутри `.app`,
переподпишите бандл: `codesign --force --deep -s - Name.app`. `tests/patch.mjs` проверяет весь
путь на Mac: изменённая программа подписывается, `codesign --verify --strict` её принимает, и
она запускается и возвращает то, что говорят новые инструкции.

## Как это устроено

- **Ядро на Rust** (`crates/`): то, что разбирает программу целиком, работает как WebAssembly.
  Там декодеры arm64, 32-битного Arm (A32, T32, VFP, NEON) и x86 (таблицы LLVM и его печать в
  синтаксисе Intel) и проходы по всем инструкциям: раскладка кода x86 и AArch32, перекрёстные
  ссылки, таблицы switch, метки и склейки HLA64. Java работает там целиком: class-файл, JAR или
  .jmod читается, его классы разбираются и каждый метод анализируется внутри, и там же пишется то,
  что страница показывает из класса, когда показывает. Так же и модуль WebAssembly: он читается, декодируется и
  анализируется внутри, а имена его функциям дают деманглеры (Rust, C++, Swift, MSVC), сверенные
  с TypeScript на 3,6 миллиона настоящих символов; так же и сборка .NET: её метаданные читаются,
  каждый метод декодируется и получает имя так, как его пишет ildasm, и там же пишется то, что
  страница показывает из неё. Контейнеры тоже читаются
  там — Mach-O, ELF, PE — и передаются странице в JSON, а причина, по которой файл не читается,
  приходит кодом, который страница переводит на свой язык. Строки HLA64 для строк листинга всех
  режимов — arm64, x86-64, WebAssembly, .NET, Java — тоже пишутся там (сессия модуля, сборки или
  JAR для них остаётся открытой); имена, которые строка использует (функции — так, как их называют
  настройки, метки, строки, импорты), знает страница, поэтому ядро спрашивает их раундами: оно
  возвращает вопросы, страница отвечает, ядро пишет строку (`crates/wasm/src/hla.rs`), а
  `tools/diff-hla.mjs` сверяет каждую строку настоящих программ с лифтером на TypeScript, который
  оно заменило. Остальное из `src/core` переезжает
  следом. `crates/core` — обычный Rust без ввода-вывода и без хоста (он собирается и нативно:
  `cargo test`, десктопная оболочка), а `crates/wasm` даёт ему C-интерфейс, и модуль ничего не
  импортирует, так что браузер, Node, Electron или wasmtime запускают один и тот же файл. Работа
  пересекает границу оптом: файл попадает внутрь один раз, проход идёт внутри шагами, которые
  задаёт страница (между ними — индикатор прогресса, а не вызов на каждую инструкцию), а
  результаты выходят один раз плоскими массивами — номер мнемоники и байт флагов на инструкцию,
  перекрёстные ссылки как отсортированные ключи, начала групп и индексы инструкций. По одному
  идут только мелкие вопросы: инструкция для видимой строки, коротким текстом JSON.
  `src/core/engine/engine.ts` — сторона TypeScript; политика страницы разрешает WebAssembly
  (`'wasm-unsafe-eval'`), а в сеть по-прежнему ничего. `tools/diff-core.mjs` сравнивает анализ с
  ядром на TypeScript, которое он заменяет, на настоящих программах: те же массивы, функции,
  ссылки и строки, в три–пять раз быстрее (arm64: 2 миллиона инструкций за 0,25 с вместо 0,9 с;
  x86-64: 4,9 миллиона за 2 с вместо 9 с).
- **Декодер** (`crates/core/src/arm64/`): таблицы кодировок A64, написанные вручную, — обработка
  данных, переходы и системные инструкции, загрузки и сохранения, включая атомарные LSE,
  скалярная плавающая точка, Advanced SIMD с FP16, скалярными произведениями, BF16, матричными
  формами Int8 и FP8 и криптографические расширения, — с псевдонимами, которые печатает LLVM
  (`mov`, `cmp`, `lsl`, `cset`, `ubfx`, …). `tools/verify-decoder.mjs` сравнивает его с
  `llvm-objdump` инструкция за инструкцией: на программе Rust из 2 миллионов инструкций
  расхождений нет, на движке Flutter для arm64-v8a (1,5 миллиона) — одно (данные, которые LLVM
  читает как SVE), а на 4 миллионах случайных кодировок расходятся только некоторые имена
  системных регистров EL2/EL3 и операций обслуживания TLB.
- **Программы** (`crates/core/src/native/image.rs`, в ядре): то, что анализу нужно от файла, —
  секции, символы, импорт, экспорт, заглушки, начала функций, метаданные Objective-C, — одинаково
  для Mach-O, ELF и PE. Образ строит ядро, и страница получает тот же образ в JSON для своих
  страниц (`src/core/image.ts`; `tools/diff-image.mjs` сверяет его с тем, что прежде строил
  TypeScript, на 16 800 настоящих программах); для анализа ядро заново читает файл, так что
  анализу целиком от страницы нужны только байты.
- **Mach-O** (`crates/core/src/macho.rs`, в ядре): универсальные файлы, сегменты и секции, таблица символов,
  импорт через таблицу косвенных символов, bind-опкоды dyld и chained fixups, export trie,
  начала функций, данные в коде, подпись кода и права. И 32-битные файлы: программы i386 для
  старой macOS, у которых точка входа часто задана состоянием потока в `LC_UNIXTHREAD` (`start`
  из crt1), идут через анализ x86; программы armv7 для старой iOS — через анализ 32-битного Arm,
  где код Thumb узнаётся по `N_ARM_THUMB_DEF` у символов, по младшему биту адресов экспорта,
  методов и `LC_FUNCTION_STARTS`, а `LC_DATA_IN_CODE` отмечает таблицы переходов. Их метаданные
  Objective-C, с 4-байтными указателями, называют методы так же, как в arm64.
- **Имена** (`crates/core/src/demangle/`, их спрашивает `src/core/demangle.ts`: имя строки — по
  одному, страница импортов — одним вызовом): символы Rust v0 и legacy и имена C++ возвращаются к
  именам в исходниках; деманглер Rust v0 совпадает с `llvm-cxxfilt` на всех символах
  тестовой программы. Имена Swift (`swift.rs`, `$s…` в Mach-O и ELF) разбираются в то
  же дерево узлов, что строит деманглер самого Swift, и печатаются так, как их печатает
  `swift-demangle`: в списке — упрощённо (`Counter.increment(by:)`, `closure #1 in
  Model.load()`, `specialized …`), в подробностях — полностью (`HelloKit.Counter.increment(by:
  Swift.Int) -> Swift.Int`). `tools/verify-swift.mjs` сверяет обе формы со `swift-demangle`
  символ за символом: на 2,13 миллиона символов Swift из Xcode и приложений в /Applications всё,
  что разбирается, совпадает; 226 редких символов (структуры-константы в специализациях,
  дженерики со значениями) остаются как есть. Имена MSVC — программ и DLL Windows
  (`msvc.rs`, `?f@@YAXXZ`) — в подробностях выглядят так, как их печатает
  `llvm-undname` из LLVM (`public: virtual int __cdecl geo::Point::length(void) const`), а в
  списке — квалифицированным именем (`geo::Point::length()`,
  `std::basic_ostream<char, std::char_traits<…>>::operator<<(…)`). `tools/verify-msvc.mjs`
  сверяет их с llvm-undname: совпадают все 1 190 имён из собственных тестов деманглера LLVM и
  все 3 412 имён библиотек среды Visual C++ (msvcp140, concrt140, vcruntime140).
- **Анализ** (`crates/core/src/arm64/pass.rs`, `crates/core/src/native/arm64.rs`, в ядре): один проход по всем
  инструкциям даёт статистику, метки, ссылки вызовов и данных, строки, на которые указывает код
  Rust (с длиной из следующего за ними `mov`), и пары, которые склеивает режим HLA64; функции и
  их имена (деманглинг — тоже в ядре) берутся из того, что говорит файл, и из того, куда идут
  вызовы, как и `main` программы без символов и заглушки PLT в ELF или таблицы импорта Windows.
  Программа на Rust в 2 миллиона инструкций анализируется меньше чем за 0,2 с — примерно вшестеро
  быстрее, чем прежним TypeScript.
- **Листинг** (`src/app/listing.ts`): миллионы строк — это два типизированных массива; рисуются
  только видимые строки, а позиция прокрутки отображается на номер строки, потому что ни один
  браузер не сделает элемент высотой 50 миллионов пикселей.
- **Страница** (`build.mjs`): код вместе с каталогами, 4,9 МБ JavaScript, и модуль WebAssembly
  ядра, 2,2 МБ, ложатся в страницу одним потоком, сжатым deflate и записанным по семь бит на символ, —
  1,9 МБ; модуль идёт байтами, а не base64 внутри кода, который deflate обратно не сожмёт; несколько строк страницы
  раскодируют его, распаковывают встроенным в браузер `DecompressionStream` и запускают. Каждый
  каталог остаётся строкой до первого обращения к нему, так что модуль WebAssembly не заставляет
  разбирать каталог x86.
- **PWA** (`build/pages/`): тот же запуск сборки записывает эту страницу как устанавливаемое
  приложение — `index.html` со ссылкой на манифест и `<meta name="service-worker">`, по которой
  страница (`src/app/pwa.ts`) регистрирует свой воркер, `manifest.webmanifest`, значки и `sw.js`
  (`src/pwa/sw.js`), который хранит страницу, чтобы она открывалась без сети. Её копия политики
  пропускает ещё три вещи, все со своего же адреса: манифест, service worker и значки, —
  `connect-src` остаётся `'none'`. Сам `build/disassembler.html` остаётся одним файлом без
  внешних ссылок.

## Сборка и тесты

В `tests/fixtures/android/` — та же программа для Android, собранная его `build.sh` с NDK:
`hello.c` в Thumb-2 и `arm.c` в A32 для armeabi-v7a, оба для arm64-v8a, без таблицы символов,

## Версии и релизы

Версия записана в одном месте — в `package.json`. Сборка ставит её в страницу (строка внизу
стартовой страницы) и в имя кэша PWA. Сборка коммита с тегом `v<версия>` показывает её как
есть; любая другая добавляет коммит, `0.1.0+1a2b3c4`, чтобы страницу из `main` на GitHub Pages
не приняли за релиз.

```sh
npm version minor           # 0.1.0 -> 0.2.0: package.json, package-lock.json, коммит и тег v0.2.0
git push --follow-tags      # тег запускает .github/workflows/release.yml
```

Workflow релиза останавливается, если тег и `package.json` не совпадают, прогоняет проверку
типов и unit-тесты, затем прикладывает к релизу `disassembler-<тег>.html` и `SHA256SUMS.txt`.
`.github/workflows/test.yml` делает то же на каждый push и pull request. Браузерные тесты
остаются локальными: они зависят от Chrome на машине CI и его скорости, поэтому их прогоняет
`npm run check` перед коммитом.

## GitHub Pages

`.github/workflows/pages.yml` собирает и прогоняет unit-тесты на каждый push в `main` и выкладывает
`build/pages/` на GitHub Pages (Settings → Pages → Source: GitHub Actions; Custom domain:
`disasm.marketkernel.com`), по адресу <https://disasm.marketkernel.com>. Программы открываются там так же, как в одном
файле, — с диска, и никуда не загружаются.

Каждый деплой меняет имя кэша в `sw.js`, так что браузер сам находит новый воркер при запуске
с сетью. Новый воркер скачивает свою версию и сразу вступает в силу: страница не хранит ничего,
что новая версия могла бы потерять, поэтому уже открытое окно продолжает работать на своём коде,
а следующий запуск или перезагрузка — уже новая версия, и без сети тоже. В этом и разница:
установленная PWA работает на том, что выложил последний деплой, а скачанный файл остаётся своей
версией. Для версии, закреплённой на диске, возьмите `disassembler-<тег>.html` из релиза и
сверьте его с `SHA256SUMS.txt`.

## Переводы

Интерфейс говорит по-английски и по-русски: **Настройки → Язык** (как в системе, English,
Русский). Переключение сразу перерисовывает всё; программа заново не читается.

- Строки интерфейса — это `t('context', 'English text')` и `tn(…)` с литералами в коде и
  `data-i18n` в шаблоне; русский словарь — `src/locales/ru.json`. `node tools/i18n.mjs`
  показывает, чего не хватает словарю и что в нём больше не нужно.
- Тексты инструкций тоже переведены: `src/data/arm64-instructions.ru.json` содержит русское
  название и описание каждой инструкции и названия условий, `src/data/hla64-words.ru.json` —
  описания слов HLA64. Английские файлы остаются источником структуры (формы, синтаксис,
  формулы, ссылки); переводы содержат только текст, и всё, чего в них нет, показывается
  по-английски.
- `tests/i18n.mjs` проверяет, что в словаре есть все строки и нет лишних, плейсхолдеры те же,
  а у русского множественного числа все четыре формы; `tests/data.mjs` — что у каждой
  инструкции, условия и слова есть русский текст.

Ещё один язык — это словарь в `src/locales`, его название в `src/core/i18n.ts` и два файла
`*.<код>.json` в `src/data`, подключённые в `src/core/catalog.ts`.

| `src/app/` | страница: шаблон, стили, листинг, панель подробностей (`cards.ts` — карточки, из которых она собирается для всех архитектур), страницы, справочник, поиск; `views.ts` — то, чем различаются виды программ, по архитектуре открытой; `wasm.ts`, `cil.ts`, `jvm.ts`, `arm32.ts`, `x86.ts`, `elf.ts`, `pe.ts` и `patch.ts` — её части для WebAssembly, .NET, Java, 32-битного Arm, x86, ELF, PE и редактирования |

## Ограничения

- Mach-O для arm64 (и arm64e), x86_64, i386 и armv7, PE для x86-64, i386, arm64 (включая ARM64EC и ARM64X) и
  32-битного Arm (Windows), ELF для arm64, 32-битного Arm, x86-64 и i386 (Android, Linux), базовые
  модули WebAssembly, сборки .NET (их IL), файлы классов и JAR Java; компоненты WebAssembly
  распознаются и отклоняются, как и байт-код Dalvik в APK (`classes.dex`) и ELF в порядке big-endian. Предложения WebAssembly FP16 и stack switching не
  декодируются (остаток такой функции показывается как `.bytes`).
- SVE и SME показываются словами `.inst`.
- Машинный код сборок .NET в смешанном режиме (C++/CLI) и ReadyToRun не показывается, только их
  IL, а листинг отмечает, где начинается каждый блок try и обработчик, вместо того чтобы рисовать
  блоки `.try { … }`, как ildasm.
- Классы JAR для других версий Java (`META-INF/versions/…`) считаются, но не показываются, а JAR
  внутри JAR (`BOOT-INF/lib` у Spring Boot) перечисляются, но не открываются.
- В библиотеке armeabi-v7a без таблицы символов данные, на которые никто не ссылается
  (таблица адресов в `.text`), показываются как инструкции — так их показывает и llvm-objdump
  без символов разметки.
- Функции берутся из таблицы символов, export trie, `LC_FUNCTION_STARTS` и целей вызовов;
  восстановления потока управления, кроме стрелок переходов и меток, и декомпиляции нет.
- Старая среда Objective-C программ i386 для macOS (сегмент `__OBJC`) не читается.
- Из метаданных Swift читаются только имена классов, видимых среде Objective-C; собственные
  дескрипторы типов и записи полей Swift не читаются.
- Из DWARF читаются только таблицы строк; строки Go, у которых нет NUL, находятся, только если
  на них указывает код.

## Лицензия

MIT. Arm A64 и AArch32 ISA XML не входят в репозиторий; в нём есть только взятые оттуда факты (имена
инструкций, формы, шаблоны синтаксиса). Описания WebAssembly написаны для этого проекта и
ссылаются на спецификацию, как и описания CIL, которые ссылаются на страницы `OpCodes` на
Microsoft Learn (авторитетный текст — ECMA-335). Таблицы декодирования x86 (`src/core/x86/tables.ts`) сгенерированы из
описания цели X86 в [LLVM](https://llvm.org), который распространяется по лицензии Apache 2.0 с
исключениями LLVM: какую инструкцию выбирает каждая кодировка, где её операнды и как она пишется в
синтаксисе Intel; декодер, который их читает, написан для этого проекта.
